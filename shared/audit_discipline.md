# 审计纪律（反幻觉 + 范围策略）

> **本文件职责边界**
> - **单一事实来源**：反幻觉铁律（代码证据、调用链标注、待验证判定）+ 审计范围策略（关注/不关注类型）
> - **不覆盖**：报告字段格式 → `report_fields.md`；覆盖率计算 → `coverage_policy.md`；验证等级 V0-V4 → `verification_principles.md`
> - **关联**：`coverage_policy.md`（覆盖率维度）、`report_fields.md`（报告格式）

本文件合并了反幻觉铁律和审计范围策略，是阶段 2/3 的核心纪律文档。

---

## 第一部分：反幻觉铁律（必须遵守）

审计报告中出现编造代码、错误行号、虚假调用链会直接破坏可信度。以下为**硬约束**。

### 1. 报告漏洞前必须用 Glob/Read 验证文件存在

- 将任何文件路径或代码位置写入报告前，必须先 Glob 或 Read 确认文件存在且可读。
- 不得根据记忆或推测写出路径。

### 2. 代码片段必须来自实际 Read 输出

- 报告中引用的所有代码片段必须来自 Read 操作结果。
- 不得凭印象改写、补全或生成代码。
- Read 时优先只读相关行区间，避免默认整文件。

### 3. 调用链每一跳必须标注文件:行号

- 数据流/调用链每一跳必须标注 **文件路径:行号**。
- 格式示例：`UserController.java:45 → UserService.java:12 → UserDao.java:33`
- 某一跳无法确定行号则标"待确认"，整条链标为待验证。

### 4. 不确定的发现标记为「待验证」

- **已确认**：完整验证可利用，PoC 可执行或调用链完整。
- **待验证**：发现可疑但无法完全确认（调用链断裂、过滤有效性不确定、版本不明等）。
- 宁可标为待验证交由人工验证，不得将不确定的标为已确认。

### 5. 不确定 ≠ 丢弃

- 证据不足以标「已确认」时，**必须标「待验证」并详细注明待验证内容**，不得直接丢弃。
- **已确认**用于完整闭环可利用的漏洞；**待验证**用于代码高度确认但部分条件需运行时验证的漏洞。两者都进入报告。
- **仅当代码分析明确证明条件不可达时**（如 Sink 前有不可绕过的白名单），才可排除。
- 误报消耗开发信任，但漏报同样有害 —— 真实漏洞被丢弃可能导致安全事件。对于已知漏洞版本的危险 API 调用（如 Fastjson 老版本 `parseObject`、XStream 无白名单 `fromXML`），**宁可多标一条待验证，不可丢弃**。

### 6. 禁止虚报目录内容不存在

- **严禁在未执行 `ls`/`find`/`Glob` 的情况下声称某目录"不存在"或"为空"**。必须用工具实际确认后再下结论。
- 若发现 `WEB-INF/classes/` 下存在 `.class` 文件，或 `WEB-INF/lib/` 下存在 `.jar` 文件，**绝对不允许**在报告中写"无 .class 业务代码"或"无 WEB-INF/lib"。
- 当发现编译产物（`.class`/`.jar`/`.dll`）存在时，必须按 `shared/decompilation.md` 执行反编译流程，**不得以"无法审计"为由跳过**。

### 7. 禁止虚假完成（anti-fake-progress）

- **禁止虚报审计进度**：声称"已审阅 X 个文件"时，`reviewed_paths_batch{N}.txt` 中必须有对应的 X 个文件路径，且每个文件必须有实际的 Read 或 Grep 操作证据。
- **禁止空跑覆盖**：不得仅 `rg --files` 列出文件名就标为"已审阅"；T1 文件必须有完整读取证据，T2 文件至少有 sink 搜索证据。
- **禁止"跳读"高风险文件**：对 T1 文件不得仅读前 50 行就跳过；Controller/Handler/SecurityConfig 等文件必须覆盖所有 endpoint 和配置项。
- **禁止选择性遗忘**：不得因为某个文件"看起来很长/很复杂"就跳过不审或留到"下一轮"（除非已达当前轮次工作量上限）。

### 8. 反流程偏离（anti-deviation）

- **禁止"换道"**：阶段 2 执行中不得突然跳到阶段 4 验证某个发现；发现有趣的漏洞时记入 findings_batch 继续审计剩余文件。
- **禁止"深坑"**：对单个文件/单个漏洞的深入分析不得超过当前轮次总工作量的 30%；如需深入追踪，记录线索到 callchain_tracker.md 并在 Phase 4 验证。
- **禁止"挑软柿子"**：不得只审简单文件而把复杂文件（大型 Controller、复杂 Service）推迟到最后几轮。批次切分时应把复杂文件均匀分配到各批次。

## 第二部分：审计范围策略

控制"什么算有实际危害的漏洞"，降低误报与无效输出。

### 关注范围（受审计模式影响）

审计关注范围由 `audit/phase0/config.json` 中的 `mode` 参数决定。两种模式的唯一区别在于**是否审计纯业务逻辑漏洞**。

**redteam + full 模式均关注**（五维框架，围绕攻防演练得分点）：

| 维度 | 关注漏洞类型 |
|------|-------------|
| **应用权限获取** | 弱口令、登录绕过、鉴权绕过、越权、JWT 伪造/签名不校验、验证码绕过、密码重置缺陷、SSO/OAuth 配置错误 |
| **主机权限获取** | RCE、命令注入、反序列化执行、SSTI、表达式注入、文件上传 getshell |
| **数据库权限获取** | SQL 注入、NoSQL 注入、获取数据库连接信息后连接执行 |
| **数据获取** | 未授权访问、任意文件读取/下载、水平越权导致大规模数据泄露、硬编码密钥/凭据、PII 大规模泄露 |
| **高危可组合漏洞** | SSRF（可访问内网/云元数据）、路径穿越、硬编码凭据、依赖组件已知高危 CVE |

**灵活判定原则**：同一漏洞类型按实际危害归类，不机械套用分类。例如：
- 文件上传条件竞争 → 可能 getshell → 属于红队模式（主机权限获取）
- 条件竞争抢优惠券 → 纯业务逻辑 → 属于全量模式

**仅 full 模式额外关注**（纯业务逻辑缺陷）：
- 支付金额篡改、0 元购、负数退款
- 订单/审批状态机跳跃
- 优惠券/积分/库存的业务规则绕过
- 竞态条件下的业务重复操作
- Mass Assignment 修改业务字段
- 业务级水平越权（未导致大规模数据泄露）

### 两种模式均不关注（不进入漏洞表）

以下类型**不作为漏洞输出**，可在残余风险或安全建议中说明：

- **DoS / 拒绝服务**（除非附带权限提升/数据泄露）
- **CSRF、XSS**（存储型 XSS 能直接获取管理员权限的除外）
- **Cookie/安全响应头缺失**（除非与具体攻击链相关）
- **代码开发规范问题**
- **纯"最佳实践缺失"**
- **猜测性结论**（无代码验证的攻击路径）

### 判定标准

一条发现要进入最终漏洞表，必须**同时满足**：
1. **有明确攻击路径**：从入口到危害有完整的数据流或逻辑链
2. **触发条件可行**：在现实部署中可达成（非纯理论场景）
3. **能造成实际危害**：获取权限、窃取数据、篡改数据、执行代码等
4. **前置条件无循环论证**：漏洞的前置条件不得与漏洞利用效果构成循环逻辑（详见 `shared/verification_principles.md` §5.1）

**⚠️ 关于"触发条件可行"的正确理解**：
- "可行"包括**代码层面高度确认但需运行时验证具体条件**的情况。例如：Fastjson 1.2.7 的 `parseObject` 调用存在于代码中，即使当前数据流来自内部服务，也不能排除攻击者通过 SSRF/缓存污染等间接控制数据源的可能 → 应标「待验证」进入报告
- "纯理论场景"是指：代码中完全不存在该危险调用、或 Sink 前有不可绕过的安全校验 → 可排除
- **已知漏洞版本 + 危险 API 调用 = 至少「待验证」**，不得以"数据流来自可信源"为由直接排除

### 输出约定

- **禁止将纯风险表述作为漏洞条目输出**。不输出「XX 可能导致 YY 风险」类描述。
- 不在默认范围内的发现不进入最终漏洞表；如对治理有价值，可进入总体建议或覆盖矩阵的残余风险说明。
- 任何不确定项标为待验证，不得标已确认。
