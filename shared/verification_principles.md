# 验证原则与漏洞类型 Playbook（阶段 4 必须遵守）

核心目标：把候选 finding 转化为可审计结论。结论必须明确区分已确认、待验证、误报/不成立，并给出验证等级、证据、限制和修复建议。优先用代码分析得出结论，仅无法从代码获知时才交人工；产出明确的漏洞，不产出模糊风险点。

本文件合并了验证原则和漏洞类型级 PoC Playbook，是阶段 4 的唯一验证参考文档。

---

## 第一部分：验证原则

### 1. 验证等级 V0-V4

| 等级 | 名称 | 标准 | 报告准入 |
|------|------|------|----------|
| V0 | 代码线索 | 仅发现危险 API、可疑版本、可疑入口或模式 | 不得作为已确认漏洞，可保留为候选或残余风险 |
| V1 | 静态可达 | 外部输入到 sink 或控制缺失可从代码闭环证明 | 可作为待验证漏洞（HYPOTHESIS），必须列出未验证条件 |
| V2 | 单元验证 | 用最小化单元测试、函数级 PoC、mock 证明关键路径 | 可进入报告，状态取决于运行时条件是否充分 |
| V3 | 集成验证 | 本地项目运行、容器、集成测试或服务级验证 | 可标已确认（CONFIRMED） |
| V4 | 授权环境 E2E | 用户提供测试环境端到端验证，记录请求、响应、预期和清理 | 最高可信已确认 |

### 2. 测试环境策略

- 用户提供测试环境、账号、授权边界时，优先做 V4。
- 没有测试环境时，不得直接放弃验证；应尝试：
  - 使用项目已有测试框架补最小化单元测试。
  - 使用 mock/stub 验证鉴权缺口、source-to-sink、过滤绕过。
  - 使用本地容器或开发配置做集成验证。
  - 只在运行时配置完全缺失或外部系统不可模拟时保留为 V1 待验证。
- 所有测试必须记录命令、输入、预期、实际结果、限制和清理方式。

### 3. 代码优先判定

对每条 finding 的每个"若 xxx"条件，必须先通过代码和配置判断，不得一律写"需人工验证"。

示例：

- 限流/防爆破：读取接口实现、网关配置、中间件配置。
- 签名校验：读取回调入口、验签函数、时间戳/nonce 校验。
- 是否对外暴露：读取路由、网关、SecurityConfig、Nginx/K8s/部署配置。
- 反序列化 source：若数据来自 Redis/MQ/DB，继续查找写入该 key/topic/table 的入口。
- IDOR/BOLA：追踪资源 ID 来源、所有权校验、租户过滤和 ORM 查询条件。
- 对"任意文件读取/IDOR"类结论，必须先分析关键参数的来源与约束。

**仅当以下情况才标"需人工验证"**：
- 运行时配置在代码中不可见
- 外部依赖行为无法从代码推断
- 部署/网络环境不在代码库内

### 4. 产出漏洞而非风险点

- **漏洞**：有代码证据，关键条件已通过代码确认或排除。
- **风险点**：仅"若 A 则 B"且 A 未经代码分析。不得作为漏洞输出。

### 5. 触发条件可行性评估

每条发现必须评估触发条件可行性：

- **成立**：触发条件在现实中可达成
- **部分成立（需...）**：部分条件待确认 → 标「待验证」
- **不成立（原因：...）**：触发条件不可达成，不得作为已确认漏洞

评估维度：
- 所需权限/身份是否真实可获得
- 关键参数是否可被攻击者获取或枚举
- 依赖配置/环境是否在生产中存在

### 6. 结论分类

| 结论 | 条件 |
|------|------|
| 已确认（CONFIRMED） | V2/V3/V4 证据充分，或 V1 静态闭环极强且运行时前提已由配置/依赖证明 |
| 待验证（HYPOTHESIS） | 代码高度确认危险模式或控制缺失，但需要运行时版本、配置、环境、数据或账号验证 |
| 不成立 | 代码分析明确证明不可达、不可控、已有不可绕过防护，或属于无实际危害项 |

不确定不等于丢弃。高度可疑但缺少运行时条件的 finding 应进入待验证或残余风险，不得伪装为已确认。

### 7. 反向审查 checklist

进入最终报告前必须检查：

- 全局鉴权、网关、Filter、Interceptor、Middleware 是否覆盖入口。
- 权限注解、策略引擎、权限表是否真实生效。
- ORM/查询构造器是否参数化，是否存在 raw SQL 拼接。
- schema validation、白名单、路径规范化是否不可绕过。
- 框架默认转义、模板 sandbox、序列化 safe mode 是否生效。
- 代码是否测试目录、样例代码、不可达代码或编译条件未启用。
- 攻击者是否能获得所需 ID、token、业务状态、租户上下文。
- 依赖版本、classpath、gadget 链是否与 PoC 假设一致。

### 8. 过滤正常业务逻辑

需要评估是否存在安全边界突破。以下情况不得作为漏洞：

- 符合业务设计且权限正确的数据访问。
- 仅代码风格、鲁棒性、DoS、日志格式、缺少安全头等无直接权限或数据危害项。
- 无外部可控入口的配置读取、环境变量读取、启动参数使用。
- 死代码、注释代码、测试代码中的不可达危险调用。
- 漏洞名称必须标准化，严禁出现类似"GET /api/xxx 在省略参数时泄露数据（Critical，需有效 Bearer）"这种混杂了等级/HTTP方法的名称。

但如果这些点能与其他漏洞形成可利用攻击链，应在阶段 5 组合分析中重新评估。

### 9. 评分和分类

- 每条漏洞必须给出 CWE。
- Web 应用漏洞映射 OWASP Top 10 和 ASVS/WSTG。
- 可评分漏洞给出 CVSS 向量、分数和每个指标理由。
- 多种触发场景对应不同权限或影响时，分别评分。
- 严重/高/中/低全部等级验证标准一致，不因"低危"而放宽证据要求。

## 第二部分：PoC/验证通用要求

### 10. 每个 PoC 的必备要素

每个 PoC/测试必须包含：

- 前置条件：目标环境、账号权限、配置、业务数据。
- 输入：HTTP 请求、脚本参数、测试用例或函数调用。
- 预期安全行为：正常应返回 401/403、参数被拒绝、查询被参数化、命令不执行等。
- 实际结果：响应码、响应体关键字段、stdout/stderr、数据库返回、日志或断言。
- 判定标准：为什么该结果足以证明漏洞存在。
- 清理步骤：删除测试数据、回滚事务、撤销账号或说明无需清理。
- 安全限制：是否只读、是否无害、是否未触发破坏性动作。
- 证据完整性：按 `shared/poc_policy.md` 记录执行时间、环境、命令/请求、响应摘要、stdout/stderr/exit code、hash 和脱敏说明。

不得使用 `TODO`、`REPLACE_XXX`、`此处从略`、省略号等空洞占位。运行时变量如 `{{access-token}}` 可以使用，但必须提供获取步骤。

### 11. PoC 安全边界

- 默认使用只读、无害、可回滚 payload。
- 需要证明命令执行时，使用 `id`、`whoami`、`echo` 等无害命令，禁止破坏系统。
- 需要证明 SQL 注入时，优先用时间延迟、错误回显、只读查询或事务回滚。
- 需要证明文件读取时，优先读取应用内测试文件或无敏感测试样本；真实敏感文件只在授权环境中按用户要求验证。
- 每个 PoC 必须包含清理步骤或说明无需清理。

## 第三部分：漏洞类型级验证 Playbook

### 12. RCE / 命令执行 / 代码执行

最低验证证据：

- 使用无害命令证明执行上下文：
  - Linux/macOS：`id`、`whoami`、`pwd`、`uname -a`。
  - Windows：`whoami`、`cd`、`ver`。
- 记录 stdout、stderr、exit code、响应时间和返回位置。
- 报告中说明命令如何从外部输入到执行 sink。
- 不允许默认执行破坏性命令，例如删除文件、写 crontab、反弹 shell、下载执行二进制。

验收标准：

- 响应体、日志、回显、异步结果或测试断言中能看到命令输出。
- 无回显命令执行必须提供可控副作用的无害证明，例如写入临时测试文件后读取并清理，或 mock 执行器断言命令参数。
- 仅代码静态闭环但无法运行时，最多 V1 待验证（HYPOTHESIS）。

### 13. SQL / NoSQL / ORM 注入

最低验证证据：

- 优先使用只读 payload。
- 时间盲注：至少包含基线请求和延时请求，记录多次响应时间差异，避免单次网络抖动误判。
- 回显/联合查询：只读取低敏元信息，例如当前数据库名、当前用户、版本、固定常量。
- 报错注入：记录数据库错误特征和拼接位置。
- ORM/raw query 注入：记录最终 SQL、查询对象或 mock 断言。

常见只读验证目标：

- MySQL：`database()`、`user()`、`version()`、`sleep(n)`。
- PostgreSQL：`current_database()`、`current_user`、`version()`、`pg_sleep(n)`。
- SQL Server：`DB_NAME()`、`SYSTEM_USER`、`@@VERSION`、`WAITFOR DELAY`。
- Oracle：`SYS_CONTEXT('USERENV','CURRENT_SCHEMA')`、`USER`、`DBMS_LOCK.SLEEP`（如具备权限）。

验收标准：

- 时间盲注要证明延时与 payload 相关，而不是网络抖动。
- 出库名/当前用户/版本必须来自目标数据库返回或测试断言。
- 禁止默认执行 `DROP`、`DELETE`、`UPDATE`、写文件、提权存储过程等破坏性动作。

### 14. 未授权访问 / 认证绕过

最低验证证据：

- 同一接口至少比较两类请求：
  - 无认证请求或低权限请求。
  - 合法高权限请求（作为预期行为对照，如条件允许）。
- 记录预期安全行为：应返回 401/403/404 或空数据。
- 记录实际行为：返回 200/业务成功码/敏感字段/状态变更。
- 证明接口影响高价值资产，例如用户数据、管理配置、权限变更、导出文件、订单/支付数据。

验收标准：

- 仅"接口可访问"不够，必须证明访问结果越过了认证或授权边界。
- 如果接口是公开设计，必须排除正常业务公开数据。
- 低权限访问高权限资源时，标题应写"越权/缺少细粒度授权"，不要误写"未授权"。

### 15. 敏感信息泄露

最低验证证据：

- 明确泄露类型：凭据、API key、JWT secret、数据库连接串、私钥、session、用户 PII、订单/支付数据、内部 URL、调试堆栈。
- 记录泄露入口、字段名、响应码、可访问权限。
- 对密钥/凭据类信息，优先验证"可用性"而不是完整展示秘密：
  - 能否用于登录。
  - 能否访问数据库/对象存储/第三方 API。
  - 能否签发或验证 token。
- 报告中展示密钥时必须脱敏，只保留前后若干字符和类型指纹。

验收标准：

- 仅版本号、普通路径、非敏感日志不默认进入漏洞表。
- 泄露内容必须能造成身份、数据、系统、供应链或横向移动风险。

### 16. SSRF

最低验证证据：

- 使用授权的本地 mock server、内网测试服务或用户提供的回连服务记录请求。
- 验证协议、重定向、内网 IP、IPv6、DNS rebinding、URL 编码等绕过点。
- 如果验证云 metadata，必须在授权测试环境中进行，并避免读取真实敏感凭据。

验收标准：

- 仅能请求公网普通 URL 不默认作为高危 SSRF。
- 能访问内网管理接口、metadata、Redis/HTTP 内部服务或可与其他漏洞组合时，进入漏洞表或组合链。

### 17. 文件读取 / 文件写入 / 文件上传

最低验证证据：

- 文件读取优先读取应用内测试文件或无敏感样本。
- 路径穿越需要证明用户输入影响最终路径，并绕过规范化/白名单。
- 文件上传需要证明存储路径、扩展名/MIME 校验、解析方式和是否可执行。
- 文件写入必须使用临时测试文件并清理。

验收标准：

- 任意文件读必须证明关键参数可控或可枚举。
- 上传漏洞必须区分"可上传任意文件"和"上传后可解析执行"。

### 18. 反序列化 / Gadget 链

最低验证证据：

- 确认反序列化 API、输入来源、依赖版本、safe mode、类型白名单。
- Java 必须检查 classpath 中 gadget 依赖；Python/PHP/.NET 需检查对应危险反序列化类型和魔术方法/危险类型。
- 有测试环境时，使用无害命令或 mock gadget 证明执行路径。
- 无法确认 gadget 时，标 V1 待验证（HYPOTHESIS），列出缺少的依赖或运行时条件。

验收标准：

- "存在反序列化 API"不是已确认 RCE。
- "假如存在 gadget"不能作为已确认依据。
- 能证明对象属性篡改影响权限、价格、状态等业务逻辑时，也可作为数据篡改类漏洞。

### 19. 多接口组合利用

最低验证证据：

- 至少由两个已确认或待验证漏洞组成。
- 写清每一步能力转移：A 漏洞拿到什么，如何成为 B 漏洞的前置条件。
- 证明组合后影响高于单漏洞，例如 SSRF 触达内网反序列化、信息泄露获得 ID 后触发 IDOR、文件读拿密钥后伪造 token。
- 输出组合链请求序列、关键响应、验证等级和未验证条件。

验收标准：

- "SSRF + 正常内网服务"不是组合漏洞。
- "信息泄露 + 猜测可能越权"不是组合漏洞，除非证明泄露值可作为后续接口参数并越权成功。
