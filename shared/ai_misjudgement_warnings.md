# LLM 审计常见误判清单

> 何时不需要读：模型对常见误判模式有较强自识别能力时；当前正在阶段 0（仅做范围与度量）。
> 何时必须读：阶段 2/3 进行候选 finding 整理与反向审查时；阶段 4 验证前的反误报核查；阶段 6 报告生成前的最终自检。

本文档记录 LLM 在代码安全审计中**最常出现的误判**与对应的正确判断方式。审计过程中遇到对应模式时必须按此表校正。

| # | 误判模式 | 正确判断 |
|---|---------|---------|
| 1 | 把 ORM 参数化查询（`#{param}` / `?` / `:param`）误报为 SQL 注入 | 参数化查询默认安全，只有 `${}` 拼接或 raw SQL 才是候选 |
| 2 | 把框架内部类（`JdbcTemplate` / `SqlSessionTemplate`）误判为业务代码漏洞 | 这是框架 API 调用，需追踪调用方的参数来源 |
| 3 | 把测试目录（`test/` / `__tests__/` / `src/test/`）中的硬编码密码当生产漏洞报 | 确认文件是否被生产 profile 或路由加载 |
| 4 | 忽略全局 Filter/Interceptor/Middleware 而误报端点未授权 | 先确认全局鉴权链是否覆盖该端点 |
| 5 | 反编译代码中变量名丢失导致误判数据流（如 `var1` 看起来像用户输入） | 追踪方法签名和调用点，而非依赖变量名 |
| 6 | 把框架自动转义（Thymeleaf `th:text` / React JSX）误报为 XSS | 确认是否使用了 raw/unsafe 输出（`th:utext` / `dangerouslySetInnerHTML` 等） |
| 7 | 把 `@RequestParam` 等注解参数未经 `@Valid` 校验就报注入 | 需追踪参数是否最终进入 raw 拼接 sink；schema 校验缺失本身不是注入漏洞 |
| 8 | 把开发环境配置（`application-dev.yml`）中的数据库密码当生产泄露 | 确认该 profile 是否被生产 `active profiles` 加载 |
| 9 | 把"静态扫描覆盖 100%"当作"漏洞域审计完成" | 必须做 OWASP Top 10 适用域一致性检查，存在域线索时要有候选或排除证据 |
| 10 | `sink_list` 命中上万条后只挑前几条写报告 | 必须分批处理全部 sink；不得截断后推进阶段 |
| 11 | 最终报告没有某类 Top 10 漏洞就默认没有 | 必须查看该 Top 10 适用域的负证据；没有负证据就是漏审 |
| 12 | 对 .NET 项目只搜 `SqlCommand`，漏掉 `QueryOptions.Where` / `FormatUtils.Format` / `FilterSql()` | 按框架特征补充 source-to-sink 追踪（含封装 API） |
| 13 | 只按单一关键词审计某个 Top 10 域，漏掉框架别名、封装函数、二次利用链 | 按项目框架特征补充同义入口、封装 API、配置点和组合调用链 |
| 14 | **循环论证前置条件**：把漏洞利用效果作为触发漏洞的前提条件，如"命令注入需要前提能在服务器上执行命令"、"SQL 注入需要数据库访问权限"、"文件读取需要文件系统访问"、"认证绕过需要管理员权限" | 前置条件只描述攻击者在利用漏洞**之前**已具备的条件（网络可达、已有身份、已知信息）；漏洞本身提供的能力提升绝不能作为前置条件。参见 `verification_principles.md` §5.1 反循环论证检查 |
| 15 | **敷衍式实战利用**：实战利用场景仅用一句话描述影响（如"可执行任意命令"、"可读取敏感文件"），不给具体 Burp 数据包 / payload / 攻击步骤，或仅把复现步骤换种说法重复一遍 | 每个实战利用场景必须包含完整 Burp 风格 HTTP 数据包或可执行脚本，从攻击者视角描述完整攻击路径（获取信息→构造 payload→发送请求→获取结果） |
| 16 | **PoC 权限与漏洞声明矛盾**：漏洞标"无需认证"但 PoC 中携带了管理员 token；或漏洞标"普通用户"但 PoC 用了管理员账号 | PoC 使用的认证级别必须与漏洞"访问权限"字段完全一致 |
| 17 | **脱离实战的 PoC**：PoC 需要极端理论条件才能成功（如"需攻击者拥有管理员同级网络位置 + 已知内部 API 密钥 + 特定时间窗口"），真实攻击者几乎无法满足 | 条件过多时应降级为"待验证"，诚实评估每个条件的现实可行性 |

## Applicability（模型代际标签）

| 误判 # | 模型预训练已覆盖度 | 何时此 Warning 可移除 |
|--------|-------------------|---------------------|
| 1, 2, 6, 7 | 高（claude-4.x / gpt-5.x 已能正确判断） | 模型升级到默认行为已规避后可移除 |
| 3, 4, 5, 8 | 中（与项目结构强相关） | 长期保留 |
| 9, 10, 11 | 低（覆盖率诚实是私有纪律） | 必须保留 |
| 12, 13 | 中（框架别名是私有知识） | 项目无 .NET / 多框架时可裁剪 |
| 14, 15, 16, 17 | **极低**（LLM 高频犯错，尤其是循环论证和敷衍 PoC） | **必须永久保留** |
| 18, 19, 20, 21, 22 | **极低**（流程偏离是 LLM 长任务的固有弱点） | **必须永久保留** |

## 流程偏离误判（审计过程级）

| # | 偏离模式 | 正确做法 |
|---|---------|---------|
| 18 | **虚假覆盖率**：声称"已审 80 个文件"但 `reviewed_paths` 中只有 30 个实际文件路径 | 覆盖率分子必须严格等于 `reviewed_paths_batch*.txt` 中的去重文件数，通过 `wc -l` 精确计算 |
| 19 | **跳读高风险文件**：对 500+ 行的 Controller 只读了前 50 行就标"已审"，遗漏后半段的管理员接口 | T1 文件必须完整读取或按 endpoint 逐个 Read 覆盖所有入口 |
| 20 | **工作量骤降**：前 3 轮每轮审 80 个文件，第 4 轮恢复后只审了 5 个就要求"继续审计" | 每轮工作量不得低于之前平均值的 50%，且必须满足 `large_project_audit.md` §8 的硬性下限 |
| 21 | **失忆式重复**：恢复后重新分析已确认的鉴权模型、重新读取已审过的配置文件 | 恢复时先读 `state.json` 的 `contextSummary`，跳过已完成的工作 |
| 22 | **深坑偏离**：在阶段 2 对某个发现过度深入（花 80% 精力验证一个漏洞），导致本轮其他文件未审 | 阶段 2 只做候选记录，深入验证留给阶段 4；单个文件/漏洞不得占当前轮次 30% 以上精力 |

## 使用规范

- 阶段 2/3 工作时按需读取；遇到与表中模式相似的候选时按"正确判断"列校正。
- 新发现的高频误判模式应**追加到本文件**，不要回写到子 SKILL 主体。
- 根 SKILL.md 仅以一行指针引用本文件，不重复列出表格内容。
