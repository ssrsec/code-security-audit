# 审计阶段定义（阶段 0 - 6）

所有中间结果必须**持久化到文件**，不依赖 LLM 记忆。

**阶段执行铁律：必须严格按顺序线性执行（阶段 0 → 1 → 2 → 3 → 4 → 5 → 6）。绝不允许“提前交付报告然后再去验证”，绝不允许跳过验证步骤，绝不允许擅自改变各个阶段的职责。**

**审计模式**：全量审计。禁止抽样。按 阶段 1 产出的应审文件列表逐文件审阅直至覆盖率 100%，未达 100% 不得进入 阶段 4。

---

## 项目根与输出根

- 用户给了路径以用户路径为准，否则以当前工作区根路径为项目根。
- 所有审计产出写入项目根下 `audit/`。
- 不得在执行中途切换到子模块目录。

---

## 阶段 0：代码库度量与反编译预处理

- **输入**：项目根路径
- **动作**：必须执行 Bash 命令 `date "+%Y.%m.%d %H:%M:%S"` 获取当前时间作为**审计开始时间**并记录。随后统计 LOC、文件数、模块数、入口数量。
  - **编译产物扫描（必须执行）**：使用 `find` 或 `Glob` **实际扫描**项目目录，确认是否存在 `.class`、`.jar`、`.war`、`.dll` 等编译产物。**严禁凭猜测声称"不存在"**。
  - **反编译预处理**：若发现编译产物且无对应源代码，必须按 `shared/decompilation.md` 执行反编译：
    - Java 产物（.class/.jar/.war） → 使用 `java-decompiler` MCP 工具反编译
    - ASP.NET DLL → 使用 `ilspy-mcp` MCP 工具反编译
    - **`classes/` 目录全量反编译；`lib/` 目录中与业务包名匹配的 JAR 也必须反编译**（如 `lib/` 下存在 `edoc2Flow-core.jar` 而项目包名为 `com.edoc2Flow`，则该 JAR 必须反编译）
    - 反编译输出路径记录到 metrics.md，后续阶段基于反编译输出进行审计
    - MCP 工具不可用时按降级策略处理，严禁跳过
- **输出**：`audit/phase0/metrics.md`（必须在文件中明确写入 `审计开始时间：YYYY.MM.DD HH:MM:SS`，若执行了反编译还需写入审计形态、反编译工具、反编译输出路径）
- **⚠️ 阶段 0 仅负责度量与反编译预处理。反编译完成后，必须正常进入 阶段 1（侦察）→ 阶段 2（审计）→ 阶段 3（覆盖率）→ 阶段 4（验证）→ 阶段 5（组合分析）→ 阶段 6（报告），严禁跳过任何阶段。反编译只是将编译产物转换为源代码形态，后续流程与审计源代码项目完全一致。**
- **完成后**：进入 阶段 1

---

## 阶段 1：项目侦察

- **输入**：阶段 0 产出 + 项目根路径
- **动作**：
  - 识别技术栈、框架、依赖
  - 枚举 API 入口，执行 Tier 分类（T1/T2/T3）
  - 初始化覆盖矩阵
  - 产出应审文件列表（覆盖率分母唯一来源）
  - 产出端点/路由清单（必须包含登录/认证/导出相关端点）
  - 产出 Sink/危险 API 清单
  - 产出依赖清单
  - 确定审计形态：source_only / compiled_only / both（无法判断必须询问用户）
- **输出**：
  - `audit/phase1/phase1_recon.md`（技术栈、入口、审计形态）
  - `audit/phase1/in_scope_files.txt`（应审文件列表，覆盖率分母唯一来源）
  - `audit/phase1/tier_list.json`（文件 Tier 分类）
  - `audit/phase1/coverage_matrix.md`（覆盖矩阵）
  - `audit/phase1/endpoint_list.md`（端点清单）
  - `audit/phase1/sink_list.md`（危险 API 清单）
  - `audit/phase1/dependency_list.json`（依赖清单）
- **完成后**：进入 阶段 2

---

## 阶段 2：全量审计（双轨）

- **输入**：阶段 1 全部产出
- **动作**：
  - **Sink-driven**：以 sink_list.md 为基准，从危险 API 往上追踪数据流，确认用户输入是否可达 Sink。
  - **Control-driven**：以 endpoint_list.md 为输入，按端点检查认证/授权/校验是否缺失。优先级 P0（未认证可达）→ P1（低权限可达）→ P2（管理员专用）。
  - T1 文件完整分析；T2/T3 先筛后读，仅对命中 Sink 或调用链引用的做完整 Read。
- **输出**：
  - `audit/phase2/findings_batch{N}.md`（候选漏洞列表）
  - `audit/phase2/reviewed_paths_batch{N}.txt`（审阅文件清单）
- **大项目**：应审文件 >200 时必须分批（每批 50-150 文件）。
- **完成后**：进入 阶段 3

---

## 阶段 3：覆盖率校验（绝对精确）

- **输入**：阶段 2 所有批次审阅清单合并 + 阶段 1 应审文件列表
- **动作**：通过精确计数计算覆盖率，严禁估算。覆盖率 = 已审文件数 / 应审文件数（必须计算具体的数字并输出比例）；更新覆盖矩阵。
- **完成度判定**：
  - 覆盖率 = 100% → 进入 阶段 4
  - 覆盖率 < 100% → 自动执行下一批补扫，循环直到 100%；仅当平台限制无法继续时才停止，并必须通过严格的文本明确报告精确进度（如“当前进度：已覆盖 125/250 个文件，精确覆盖率 50.0%”），随后**只能**提示用户输入「继续审计」，**绝不能提供跳过流程或提前生成报告等任何其他选择**。
- **输出**：更新 `audit/phase1/coverage_matrix.md`、`audit/phase2/coverage_status.json`

---

## 阶段 4：漏洞验证与评分

- **输入**：阶段 2 候选漏洞 + 依赖版本信息
- **动作**：
  - 查阅漏洞成立条件知识库，结合版本/配置判断是否成立
  - 代码优先判定每个"若xxx"条件，不一律写"需人工验证"
  - 参数与业务逻辑分析（对任意文件读取/IDOR 等必须分析参数来源与约束）
  - 触发条件可行性评估
  - CVSS评分（中文表述）
  - 反幻觉检查
- **输出**：`audit/phase3/findings_verified.md`（含「已确认」和「待验证」两类漏洞。代码层面高度确认但需运行时验证部分条件的漏洞标「待验证」并详细注明待验证内容，**严禁因 payload 不完美而丢弃**。每条必须满足报告必填字段。）
- **完成后**：执行组合漏洞分析

---

## 阶段 5：组合漏洞分析（必须执行）

- **输入**：findings_verified.md 中全部已确认/待验证漏洞
- **动作**：按 `shared/composite_vulnerability_analysis.md` 分析漏洞组合，识别攻击链。
- **输出**：`audit/phase3/composite_findings.md`
- **完成后**：进入 阶段 6

---

## 阶段 6：最终报告

- **输入**：findings_verified.md + composite_findings.md
- **动作**：按报告模板生成唯一交付报告，严格遵守 `shared/report_fields.md` 定义的字段。
- **输出**：`audit/security_audit_report.md`（唯一交付物）
- **完成度**：每条漏洞满足全部必填字段方可输出
