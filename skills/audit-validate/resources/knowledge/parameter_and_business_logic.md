# 参数与业务逻辑分析（通用）

**适用**：所有语言与框架。在认定「未授权访问某资源」「任意文件读取/路径遍历」「IDOR」等结论前，必须结合源码分析**关键参数的生成与约束**，避免误报。

---

## 原则

- **先分析再下结论**：漏洞结论必须建立在「关键参数是否可被攻击者控制或枚举」的基础上。
- **通用**：不依赖具体语言/框架；参数名（如 configId、path、resourceId、token）仅为示例，实际按项目中的标识符、路径、ID 等分析。

---

## 关键参数类型（示例）

| 参数含义       | 可能形态（依项目） | 需分析的问题 |
|----------------|--------------------|-----------------------------|
| 资源/存储 ID   | configId、bucketId、tenantId、storageId | 如何生成？可枚举/猜解吗？（如自增、UUID、来自库表且不可预测） |
| 路径/键        | path、key、file、uri                    | 是否用户可控？是否做规范化/白名单？是否存在 `..` 或绝对路径？ |
| 对象/实体 ID   | id、userId、orderId、documentId         | 来自请求体/URL 时，是否有权限校验？是否可遍历/枚举？ |
| 令牌/凭据      | token、ticket、signature、nonce         | 如何签发？是否可伪造或重放？有效期与绑定范围？ |

---

## 分析动作（源码中做）

1. **溯源**：该参数从哪里来？（请求参数、Header、Cookie、上游服务、数据库、配置文件）
2. **生成方式**：若由服务端生成，是否有规律可猜解？（如自增 ID、短随机数、可预测 UUID）
3. **约束**：是否有白名单、长度限制、格式校验、权限校验（仅限某角色/某租户可访问该 ID）？
4. **组合**：若结论依赖多个参数（如 configId + path），需**同时**分析；例如 configId 为 UUID 且无枚举途径时，单凭 path 用户可控也不构成「任意文件下载」，需在报告中限定为「待验证：若 configId 可获知则 path 可控存在路径遍历风险」。

---

## 报告约定

- **不直接下「任意 XXX」结论**：除非已确认关键参数可被攻击者控制或枚举；否则标题与结论中限定为「待验证」并写明缺失的假设（如「需确认 configId 是否可枚举」）。
- **标题**：以**漏洞类型**为主（如「未认证路径遍历（path 用户可控，configId 待确认）」），不写成长句实现细节（如「文件下载接口 @PermitAll 且 path 来自请求 URI」）。
- **漏洞原理/触发条件**：写明「关键参数 configId 在源码中由 XXX 生成/约束，若可枚举则…」或「configId 为 UUID 无枚举途径，当前不构成任意文件下载」。

---

## 示例（与框架无关）

- **文件/存储读取**：若接口存在 path 或 key 参数，需查 configId/storageId 等从何而来；若为 UUID 且仅授权接口可获知，则不能报「未认证任意文件下载」，可报「未认证文件读取（path 可控，存储 ID 需授权获知，待验证）」。
- **按 ID 访问资源**：若 id 来自 URL 且无权限校验，需确认 id 是否可枚举（自增则高危；UUID 且无列表接口则风险降低）；在结论中区分「IDOR（id 可枚举）」与「IDOR（id 需已知，待验证）」。
- **管理后台/敏感路径**：若整站已限制为某角色（如仅管理员）且业务无细粒度角色，则「仅缺某操作权限注解」不作为漏洞，见 authorization_model.md「先理解业务逻辑再判定」。
