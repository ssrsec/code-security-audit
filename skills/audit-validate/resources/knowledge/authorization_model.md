# 授权/拦截层通用审计要点

供 阶段 2 Control-driven 使用。当发现「按 URL/路由做权限控制」时，按本页要点检查授权层设计缺陷；**框架无关**，适用于 Java/Spring、Node/Express/Koa、Python/Django/Flask/FastAPI、PHP/Laravel、.NET、Go 等。

---

## 何时视为「授权层」

以下任一存在即视为项目的授权/拦截层，需单独过一遍本页检查：

- **拦截器/中间件/装饰器**：在请求到达业务 Handler 前做「是否放行」判断（如 Java `HandlerInterceptor`、Node `middleware`、Python `@login_required` / 中间件、PHP 全局 filter、.NET `AuthorizationFilter`、Go `middleware`）。
- **权限表/路由-角色映射**：配置里或数据库中「URL/路由 ↔ 角色/权限」的映射（如 Spring SecurityConfig、权限表/ACL、Node 的 route meta、Django 的 permission decorator、Laravel 的 gate/policy 等）。
- **网关/反向代理**：在网关层按 path 做鉴权或放行（如 Kong、APISIX、Nginx + lua）。

---

## 三类常见缺陷（通用）

### 1. 匹配方式过宽（子串/前缀导致越权）

- **现象**：用「请求 path 是否包含某字符串」或「是否以某前缀开头」来判断权限，而不是精确 path 或 method+path。
- **常见写法**（仅举例，不穷举）：
  - 字符串包含：`url.indexOf(perm) >= 0`、`path.contains(perm)`、`strpos($uri, $perm) !== false`、`strings.Contains(path, perm)`。
  - 前缀匹配：`path.startsWith(perm)`、`url.startsWith(perm)`、`path.match(/^\/api\/admin/)` 但权限表只配了 `/api/admin`。
- **风险**：授予 A 路径权限后，可访问 A 的任意子路径（例如有 `/score` 就能访问 `/score/update`）；或短路径被长路径包含（有 `/notice/list` 却因匹配到 `/notice/` 而访问到 `/notice/delete`）。
- **检查**：列出所有业务接口与权限配置中的 path；看是否存在「包含关系」导致不应放行的 path 被放行。

### 2. 权限表/配置缺漏（未授权访问）

- **现象**：业务接口未出现在权限表/路由权限配置中，或某角色未配置却能被拦截器放行（如拦截器只放行「在白名单中的 path」，而新加的接口未加入白名单导致所有人可访问；或反之，未加入需授权列表导致未校验）。
- **常见形态**：新增 Controller/路由后未在权限表/ACL 中登记；某环境只配置了部分 path；默认策略是「未配置即放行」或「未配置即拒绝」与预期不符。
- **检查**：枚举所有业务入口（Controller 方法、路由定义、装饰器下的 handler）；与权限表/ACL/中间件配置逐条对照，找出「未配置」或「默认策略不当」的接口。

### 3. 白名单/顺序/默认策略不当

- **现象**：静态资源、登录、验证码等本应放行，却依赖「权限表不包含即放行」导致业务接口也被放行；或拦截顺序错误（先放行再鉴权）；或默认 deny/allow 与设计相反。
- **检查**：确认放行列表是否最小化；拦截链顺序是否合理；默认策略是否与「最小权限」一致。

---

## 简短判定流程（按顺序做即可）

1. **定位授权层**：找到拦截器/中间件/装饰器/网关中「根据 path 或路由决定是否放行」的代码与配置（含权限表、ACL、环境配置）。
2. **看匹配逻辑**：若为「包含/前缀」匹配，列出所有权限项与所有业务 path，检查是否存在包含关系导致的越权或误放行。
3. **看覆盖度**：用业务入口列表与权限配置做 diff，找出未在权限表/ACL 中登记或与预期角色不符的接口，标为未授权访问候选。
4. **看白名单与默认**：确认放行列表、拦截顺序、默认策略无过宽或矛盾。

---

## 输出约定

- 发现「匹配过宽」：记为授权逻辑缺陷（可与具体越权组合，如「权限表授予 /score 且无角色校验，导致可访问 /score/update」）。
- 发现「权限表缺漏」：记为未授权访问候选，在 阶段 4 结合业务确认是否真实可访问（如是否被其他层拦截）。
- 不写框架专属规则；不维护正则库；仅提醒 AI 在发现 URL 权限控制时执行上述检查。

## 漏洞类型用词约定（避免误读）

输出时必须区分以下三类，**不得**在「已需管理员/登录」的接口上使用「未授权访问」作为主标题，以免被理解为「谁都能访问」：

| 场景 | 推荐用词 | 说明 |
|------|----------|------|
| **无需登录即可访问** | 未认证访问 / Missing Authentication | 接口为 permitAll、或未在受保护路径下，任何人可请求。 |
| **低权限访问高权限资源 / 操作他人数据** | 越权访问 / 未授权访问 / IDOR | 例如普通用户可访问管理员接口、或可操作他人数据。 |
| **需登录（或需管理员）但缺少细粒度权限校验** | 权限校验不完整 / 缺少细粒度权限 | 接口已在「需认证」或「需管理员」保护下，但未校验与同模块一致的**操作权限**（如缺少 @PreAuthorize("system:user:query")）。**不得**标为「未授权访问」；应在描述中写明「需管理员（或已认证）登录，但未校验 XXX 权限」。 |

**示例**：某接口在 /admin-api/ 下、需管理员 Token 才能访问，但未加 @PreAuthorize("system:user:query")。应记为「**权限校验不完整**：需管理员登录，但未校验 system:user:query，与同模块 /page 不一致」，**不要**记为「未授权访问」。

---

## 先理解业务逻辑再判定（避免误报）

审计时必须先理解业务逻辑，以下情况**不应**作为漏洞输出：

1. **管理后台已限制为「仅管理员可登录」**（如 /admin-api/ 需管理员 Token、网关或统一拦截器已校验）  
   - 若业务上**未区分**多种管理员角色（如超级管理员 vs 普通管理员、或没有「某管理员只能看 A 不能看 B」的权限矩阵），则「仅缺少 @PreAuthorize、无低权限用户可访问」的接口**不作为漏洞**输出。  
   - 原因：能登录管理后台的本身就是管理员，业务上即具备这些操作权限；只有存在**细粒度角色**且该接口应限制为某子权限时，才报「权限校验不完整」。

2. **仅限登录用户、且仅为下载模板/静态结构、无敏感数据**  
   - 例如：登录后下载「导入模板」（Excel 表头/空结构）、静态说明文件等，从业务角度属于正常能力，**默认不作为真实危害**输出；可标为 Info 或 Out-of-scope。

## 权限颗粒度细化：认证 / 授权 / 租户隔离（三维）

同一个端点可能同时涉及三类控制，**不能**只看到某个注解就下结论（例如把「免授权」误当成「免认证」）：

1. **认证（Authentication）**：是否必须登录/持有有效凭证才能访问
2. **授权（Authorization / RBAC / ABAC）**：登录后是否仍需具备某个角色/权限/资源归属才能访问或操作
3. **租户隔离（Tenant Isolation）**：在多租户系统里，是否限制只能访问本租户数据；忽略租户可能导致跨租户读取/修改

### A. `@PermitAll` / `allowAnonymous` / `permitAll` 的语义必须以代码为准

不同框架/项目对“允许访问”的实现方式不同，常见至少有两种语义：

- **语义 1：免认证**：未登录也可以访问（真正的 public endpoint）。通常体现为路由匹配规则/中间件直接放行。
- **语义 2：仅跳过细粒度授权**：仍要求登录，但不做角色/权限校验（相当于“任意已登录用户都可访问”）。

**审计要求**：发现此类注解/配置时，必须回到实际拦截链判定它属于哪一种：

- **看路由匹配/安全配置**：是否把该路径加入了 `permitAll/anonymous` 白名单，且存在 `anyRequest().authenticated()` 或等价兜底规则
- **看认证过滤器是否仍运行**：是否仍会校验 token/session；若认证失败会不会被拦截（401）还是继续放行（200/业务错误）
- **看方法级授权是否被绕过**：是否只是绕过 `@PreAuthorize` / permission check，而认证仍在

结论输出时必须写清：**“无需认证”** or **“需登录但不限制角色/权限”**。

### B. `@TenantIgnore` / `ignoreTenant` 不等于权限放行

`TenantIgnore` 类注解的含义通常是：**跳过租户自动过滤/租户上下文约束**，它本身不代表免认证/免授权。

- 若端点同时是 public（免认证）或“任意已登录用户可访问”，且又忽略租户过滤，则需要进一步审计是否形成 **跨租户数据访问/修改**。
- 若端点为后台管理员专用，但忽略租户过滤仍可能导致“管理员可读取全租户数据”的设计风险，是否漏洞取决于业务预期与权限模型。

输出候选时优先使用更精确的标题：

- 「未认证访问（…）」仅在确认免认证时使用
- 「已认证但缺少授权（…）」用于“任意登录用户可访问”
- 「租户隔离绕过（@TenantIgnore，…）」用于跨租户访问风险
